# Recommendation Engine Plan

BetterBoxd now uses a frontend implementation that mirrors the production recommender shape without requiring paid embedding calls during local use.

## Current App Logic

- Ratings are the strongest signal.
- Watchlist adds are weaker positive signals.
- Taste Sprint responses influence the profile.
- Onboarding genres, favorite movies, and directors are optional.
- Recommendation modes change the ranking mix:
  - Focused: mostly semantic similarity.
  - Balanced: similarity with some popularity and novelty.
  - Exploratory: more diversity and novelty.
- Recommendation impressions and outcomes are logged locally so ranking modes can be compared.
- Recommended movies include short deterministic explanations based on preference overlap, keyword overlap, similar high-rated movies, watchlist overlap, TMDB relationships, or rating quality.
- Candidate coverage is expanded by a bounded local movie catalog cache fed from TMDB trending, popular, top-rated, upcoming, search, and viewed details.
- Final recommendation lists use diversity reranking so top results are not all near-duplicates.

The local app uses deterministic hashed embeddings from canonical movie profiles generated by `buildMovieProfile(movie)`. These profiles include title, overview, genres, keywords, director, cast, country, language, decade, and TMDB relationship fields. This keeps the app free to run while preserving the same vector-search model shape used by real embeddings.

Recommendation and fallback search share the same local embedding adapter. Ask BetterBoxd can additionally call the server-side OpenAI semantic route for fuzzy ranking, while retaining the local profile-based fallback when that route or key is unavailable.

When a TMDB key is configured, trending and search results are enriched with a bounded number of detail requests. Those detail records add keywords, credits, production countries, and TMDB similar/recommended movie relationships. The cap keeps the app responsive while giving the recommender more useful signals than short overviews alone.

## Feedback Logging

The app records lightweight events in `localStorage`:

- `impression`: a recommended movie was shown.
- `open`: the user opened a recommended movie.
- `watchlist`: the user saved a recommended movie.
- `rating`: the user rated a recommended movie below 4 stars.
- `highRating`: the user rated a recommended movie 4 stars or higher.

Only user-relevant summary feedback is shown in Profile:

- movies opened from recommendations
- movies saved or highly rated from recommendations
- the recommendation mode currently performing best

Raw analytics stay out of the product UI.

## Current Semantic Search Boundary

`api/semantic-search.ts` embeds the query and the same canonical movie-profile fields on the server. It enforces request, candidate, field-length, cache, and basic per-instance rate limits. Its warm-instance embedding cache is an optimization, not durable storage, and the route falls back to local profile matching when unavailable.

## Production Upgrade

Move the existing OpenAI `text-embedding-3-small` movie vectors into a durable cache and query them through `pgvector`. Public movie metadata can be embedded once; user personal data should not be sent to the embedding API.

Recommended backend:

- PostgreSQL
- `pgvector`
- server-side TMDB sync
- server-side OpenAI embedding job

The user taste vector should be computed from stored movie vectors:

```text
taste = weighted_average(
  ratings,
  watchlist adds,
  onboarding favorite movies,
  onboarding genres,
  onboarding directors
)
```

Candidate ranking:

```text
final_score =
  semantic_similarity * mode_similarity_weight
+ normalized_popularity * mode_popularity_weight
+ normalized_vote_average * mode_rating_weight
+ novelty_score * mode_novelty_weight
+ preference_boost
```

Rated and watchlisted movies should be excluded from recommendations.

After scoring, the app reranks candidates with a mode-sensitive diversity penalty. Focused mode stays closest to the raw score; Exploratory mode applies the strongest penalty to movies that are too similar to already-selected recommendations.

## Suggested Schema

```sql
create extension if not exists vector;

create table movies (
  tmdb_id bigint primary key,
  title text not null,
  release_year integer,
  poster_path text,
  overview text,
  genres text[] not null default '{}',
  director text,
  cast_names text[] not null default '{}',
  vote_average numeric,
  popularity numeric,
  embedding vector(1536),
  embedding_model text,
  embedding_updated_at timestamptz
);

create table user_movie_interactions (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null,
  tmdb_id bigint not null references movies(tmdb_id),
  rating numeric,
  watchlisted_at timestamptz,
  interest text check (interest in ('interested', 'maybe', 'notInterested')),
  watched_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table user_onboarding_preferences (
  user_id uuid primary key,
  genres text[] not null default '{}',
  directors text[] not null default '{}',
  favorite_tmdb_ids bigint[] not null default '{}',
  updated_at timestamptz not null default now()
);

create table recommendation_events (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null,
  tmdb_id bigint not null references movies(tmdb_id),
  event_type text not null check (
    event_type in ('impression', 'open', 'watchlist', 'rating', 'highRating')
  ),
  recommendation_mode text not null check (
    recommendation_mode in ('focused', 'balanced', 'exploratory')
  ),
  recommendation_score numeric not null,
  created_at timestamptz not null default now()
);

create index movies_embedding_idx
  on movies using ivfflat (embedding vector_cosine_ops)
  with (lists = 100);
```
